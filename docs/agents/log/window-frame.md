# Self-Correction Log: Window frame, DPI, placement and quick terminal

Part of the Self-Correction Log; [AGENTS.md](../../../AGENTS.md) indexes the area files and says how to add an entry. Newest first.

- 2026-10-16: In a real drag onto a monitor of another DPI, Windows resizes the window to its linearly scaled size before `WM_DPICHANGED`, while the old font is still installed (a 935x644 client at the 144-DPI font, about 66 columns, on its way to 96 DPI). Every `WM_SIZE` handed that size to the core, so termio could wrap long lines into scrollback before the font changed. The host now holds core sizes and fonts from `WM_GETDPISCALEDSIZE` (sent first) to `WM_DPICHANGED`. There each surface takes its font and size inside a core resize batch (`beginResizeBatch`/`endResizeBatch`), which sends termio one resize. Measured with logging of core sizes and termio grids: main + #423 sent an old-font size on 30 of 30 real drags and pushed rows into scrollback on 20 (up to 16 rows); with the hold, 0 of 30. Traps:
  - termio's resize coalescing does not restart its 25 ms timer, so a resize sent first in a burst is applied if the burst outlasts 25 ms. Ordering font before size is not enough; batch them.
  - `WM_DPICHANGED`'s `SetWindowPos` runs a nested layout that called `syncContentScaleToHostDpi`, which changed the font outside any batch. With a 60 ms injected delay, the batch alone changed nothing until that call was held too.
  - The logging changed the odds: an uninstrumented baseline lost the race in 0 of 30 drags, and end-state screenshots could not tell the builds apart.
  - A held size must not be recorded in `Surface.size`, or the sync after the hold sees no change.
  - Check that the maintainer is away before any visible run. The last batches started with their game (`UnityWndClass`) in the foreground, and the harness took focus from it on every drag.

Maximized sources keep `maximizeWithPlacement` and their own normal rect. Test traps: the `TestSession` fixtures create no chrome window classes, so `activateSurface`, `showHostSurface` and `Host.layout` on a host with a tab fail inside `refreshChrome` and leave `cached_window_title` behind, which the leak check fails (set `quick-terminal-keyboard-interactivity = none`, detach the tab, or free that string); `EnumChildWindows` in the harness also lists a surface detached for undo, so pick the visible pane; a `-Dtest-filter` token with a space does not survive `cmd.exe //c`; and `cmd.exe //c wrapper.cmd` does not search the current directory (use `.\wrapper.cmd`). Still open: saving a named layout from the quick terminal says "Layout could not be saved." - 2026-10-06: Entering fullscreen from a maximized window and leaving it left the window's normal rect at the maximized size, so un-maximizing afterwards kept it screen-sized. This refines the 2026-09-24 entry below, which put it down to `restore_rect` being captured while maximized: that was half of it. A window that was maximized is maximized again with `ShowWindow(SW_MAXIMIZE)` and only then given its old placement through `SetWindowPlacement`, which on a window that is already maximized rewrites just the normal rect. Any other window keeps the exact `SetWindowPos` restore, with its topmost handling. For a snapped window that also keeps the snapped rect, because its placement holds the pre-snap rect; that part is inferred, since a hidden desktop takes no shell input and snap was never measured. (3) A unit test that maximizes a window shows it, so it must run on a desktop of its own: `CreateDesktopW`, then `SetThreadDesktop` on a fresh `std.Thread`. `SetThreadDesktop` fails on a thread that owns any window or hook (documented), and the test runner's thread is the one every other win32 test creates windows on. (4) `SetWindowPlacement` with `SW_SHOWMAXIMIZED` does not set the normal rect and maximize in one step when the window is still normal. An out-of-context `EVENT_OBJECT_LOCATIONCHANGE` trace of the real app showed it first moving the window to the normal rect, (300,200) 1400x900, for about 10 ms, and only then maximizing it: 8 location changes where maximize-first takes 6. Still open: after a monitor change while fullscreen, the normal rect is not moved to the new monitor. A later restore goes back to the old monitor with the size scaled by the DPI ratio (1400x900 came back 2100x1350, and 667x467 came back 445x311).
